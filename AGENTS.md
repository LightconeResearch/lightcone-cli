# AGENTS.md

This file provides guidance to coding agents working in this repository.

## What this is

**lightcone-cli** ships `lc`, the execution layer for ASTRA 0.1 (`astra.yaml` analysis specs). The split is enforced in code: `astra-tools` owns what a spec *means* — validation, universes and their selections, what each result reads, where it goes, and its command as it runs. `lc` asks for it with `astra.api.resolve` and never re-derives any of it. `lc` owns execution: scaffolding, environments, sandboxing, deciding what to remake from ASTRA's checker (`astra.api.status`), running recipes, committing results with ASTRA's record of each (`astra.api.write_records`). lc imports astra through `astra.api` alone; if something about spec meaning looks wrong, or `astra.api` lacks what lc needs, the fix is a PR to astra-tools, not a second implementation or a reach into its internals here.

User documentation lives in a separate repository (LightconeResearch/docs), not here.

## Commands

```bash
uv sync --group dev                 # pytest, ruff, mypy, datalad
uv run pytest                       # whole suite
uv run pytest tests/test_plan.py::test_name   # one test
uv run ruff check src/ tests/       # --fix to apply
uv run mypy src/                    # strict
uv run lc --help                    # the CLI from the checkout
uv build                            # wheel + sdist
```

There is deliberately no task runner. CI (`.github/workflows/{tests,lint}.yml`) runs exactly pytest, ruff and mypy — Linux on Python 3.11–3.13, plus macOS on 3.13.

Several suites skip when their prerequisite is absent, and CI turns each skip into a failure with an environment variable. Set the same variable locally to be sure a suite really ran:

| Variable | Suite | Needs |
|---|---|---|
| `LC_SANDBOX_TESTS_REQUIRED=1` | `test_sandbox_enforcement.py` | Landlock (Linux) or Seatbelt (macOS) |
| `LC_CONTAINER_TESTS_REQUIRED=1` | `test_container_smoke.py` | podman or docker |

The `uv-floor` CI job reruns the uv-touching suites against uv 0.7.0. That version must equal the `required-version` floor in `src/lightcone/engine/templates/files/pyproject.toml.tmpl`; change both together. The job is commented out in `tests.yml` while lc depends on release candidates of astra-tools: a `datalad rerun` installs lc by name, and uv 0.7.0 refuses a pre-release that a dependency of a dependency asks for. Re-enable it once `pyproject.toml` asks for final releases.

## Architecture

### Layout

- `src/lightcone/` is a **PEP 420 namespace package: it must never contain an `__init__.py`**. Sibling `lightcone-*` distributions share the namespace, and `python -m lightcone._sandbox_exec` relies on it to import nothing else.
- `cli/` holds flags, rendering and exit codes only. Logic lives in `engine/`, which raises `ProjectError`; the click group translates it.
- Module docstrings are the design record for each module. Read the docstring before changing a module.

### The model

A project is `pyproject.toml` + `uv.lock` + `.python-version` + `astra.yaml`, in a git repository with git-annex. uv is the only environment substrate. The current directory is the project root; nothing walks up.

- **Convergence** (`project.py`, `lc init`): every item is created if missing and repaired if wrong; rerunning is always safe. Scaffolded file content lives as real files in `engine/templates/files/*.tmpl`.
- **Graph** (`plan.py`): one task per result of the working tree, keyed by ASTRA's id for it (`fit#baseline`; `fit` for an output built once; `stage.fit#u1` for a result of an analysis the project drives; `stage:fit#v1` for one of an analysis it declares), in ASTRA's order: each after every result it reads. A result is exactly one file at the place ASTRA gives it, `<analysis>/results/<universe>/<name>.<format>`, with ASTRA's record of it at `<analysis>/.astra/records/<universe>/<name>.json`; the record is all lc writes beside a result. `build` asks `astra.api.resolve` and `astra.api.status` once each, refuses the pair where they name different commits, and keeps the checker's whole report beside the tasks (`Graph.checked`). A `Task` is ASTRA's own `Result`, its places included, with what a run needs looked up once: the folder its recipe runs in, the file each entry reads and what its recipe asks for. ASTRA renders the command and gives every path; lc composes neither.
- **Declared analyses** (`plan.py`, `commits.py`): an analysis the project declares by path is built like its own, each recipe in its own analysis's folder. Each is inside the project's folder: whatever a run reads or writes of the working tree is there, so the dirty-tree check, the sandbox's read root and a container's mounts are the project's alone. One outside it (`path: ../shared`) is refused; declared with a `commit`, its results are read. A result from a commit is no task: it is read through its record at that commit. Whatever a recipe reads at another commit, a run gives it in that commit's tree: `.lightcone/commits/<commit>/` (`plan.COMMITS`) is a clone of the repository that holds the commit — the URL its analysis is declared with, or the project's own — checked out at it, and `astra.api.resolve(commits=...)` names each such file there. Refused as well: a recipe that would run on a commit's files (`NOT_AT_COMMIT`), and an analysis in a repository of its own.
- **Identity** (`identity.py`): `env_version` (raw `uv.lock` bytes, `.python-version`, a closed list of uv install settings, the image declaration) is the environment's identity, and a record names it as the IRI `urn:lightcone:env:<env_version>` (`identity.environment`), a function of the files `identity.files` names in the record's commit. What a result is *made from* (its declaration, the options selected, its inputs' content, the results it reads) is the specification's, compared by ASTRA's checker against the commit the record names. There is no definition hash here.
- **Classification** (`plan.classify`): one rule, shared by `lc status`, `materialize --check`, `materialize` and `lc fetch`. A result's state is ASTRA's checker's — `ok`, its `unchanged`; `stale`, where something it is made from changed since the commit its record names, or something it reads did; `missing`, with no valid record — plus lc's `behind`: ok, but made under another environment than the project's, reported and remade only with `--refresh`. Where ASTRA's checker leaves off, at what can be fetched, lc says what a clone has to do to hold each result current: it calls `stale` a result whose place holds other bytes than its record gives (ASTRA's `ABSENT_RESULT`, a warning beside an `unchanged` state), and `missing` one whose bytes this clone lacks and none of its remotes holds (`dataset.holders`); on those, and `behind`, `lc status` and `astra status` differ. `stale` and `missing` are remade. An ok or behind result whose bytes a remote holds needs a transfer, not compute: `lc status` marks it unfetched, `lc fetch` brings it, and a run fetches it only where a recipe reads it. So a state is the clone's, not the commit's: a commit whose bytes were never pushed is up to date where it was made and `missing` in every clone of it, and `--check` fails there. `lc status` shows the state and the commit, never the reason; `--json` and `materialize --check` give it.
- **Execution** (`materialize.py` drives, `worker.py` makes one result): the driver refuses a tree that holds uncommitted work, takes a checkout of the commit, hands the graph to Dask, and **owns git alone**, committing each result in the project's tree as it arrives, with its record in the same commit. Workers never raise and never write git; a failed task returns an outcome saying so.
- **Checkout** (`checkout.py`): every recipe of a run runs in a tree of the run's own, a linked git worktree of the commit the project is at when the run takes it, under the project's ignored `.lightcone/runs/`. The project's tree stays the researcher's: what is edited, staged or committed there while a run is in flight is no part of it, and each run has its own checkout, so several runs of one project share only the repository. git-annex never runs in a checkout; lc gives the files a run reads their bytes as one more name for the annex's own objects. A result is written once: its recipe writes it in the checkout, its worker moves it to its place in the project's tree, and the driver commits it there in place, where git-annex runs as it always has. A checkout is held by git's own worktree lock, which names the run's allocation, and is gone once the run has heard from every task, or once that allocation has ended. Each commit carries a DataLad run record that names `python -m lightcone.engine.worker <task>`, so `datalad rerun` reproduces it: datalad fetches the files of the dataset the record lists, and the worker gives the trees of other commits itself, from the analysis at that commit.
- **Storage** (`dataset.py`): the DataLad model through plain `git` and `git annex`. `.gitattributes` routes results and declared inputs to the annex with `filter=annex`; records and code stay in git. Whether a file holds its content or only a stand-in for it, and the hash a record names content by, are `content.py`'s.
- **Publication** (`publish.py`, `github.py`): `lc publish` converges one statement — the repository on GitHub holds the current branch, and the project's *store* holds the bytes of every file its commit names. GitHub holds git, not what git-annex keeps, so the bytes have a home of their own: the repository's Git LFS storage, or a git-annex repository in a directory on the group's cluster. The store is declared once, at the first publication, in git-annex's branch, as a special remote git-annex enables by itself; every clone learns it with nothing to configure, and nothing about a publication is kept in a file or setting of lc's own, so DataLad clones, gets and pushes a project without lc. Two things are never decided by lc: who may read the project (`--private` or `--public`, no default, and public only when asked), and whether a store another clone declared is where this clone's bytes go (`--confirm-data`). One publication sends bytes, then git-annex's log, then commits, and merges nothing. `github.py` is the REST API through the standard library, behind one function (`_call`); `gh` is never needed.
- **Exec boundary** (`sandbox/`): `policy.py` builds mechanism-free path sets; a `Backend` is a pure `wrap(policy, argv) -> argv`; `boundary.py` picks the backend, runs it and returns an `Attestation` of what was actually enforced. The backends are Landlock (through the stdlib-only shim `_sandbox_exec.py`), Seatbelt (generated SBPL), and OCI (podman, podman-hpc, docker), where the mount table is the mechanism. The tree is read-only apart from the write scope. Network is deliberately not controlled. `lc run` puts a probe under the same boundary a recipe gets, in the project's own tree: a probe reads what is there, committed or not, where a recipe reads what its run's commit holds and its output declares.
- **Containers** (`image.py` pure, `container.py` impure): declaring `[tool.lightcone.image]` in `pyproject.toml` switches the project to containerized mode. Nobody authors a Containerfile. The built image is saved as a docker-archive, annexed and committed in the repository; runtimes load it from there, and their local stores are only caches.
- **Compute** (`compute/`): allocation is explicit. `lc compute launch` starts a local or Slurm Dask cluster from an offer in the catalog, and `lc run` / `lc materialize` take its name or ID as their first argument. Providers own the native lifecycle; the engine borrows a standard Dask client.

### The runner's rules

The specification's table of rules has a runner layer, and `lc` is who answers for it. Each rule lc keeps is kept in one place, and `tests/test_runner_rules.py` has a test named after it.

| Rule | Where lc keeps it |
|---|---|
| `UNRECORDED_RESULT` | `worker.execute`: the recipe writes the result's default place, and `astra.api.write_records` writes a record at each of its places, committed with the bytes. |
| `FALSE_RECORD` | `worker.execute`: the result's hash is of the file the recipe wrote; each input's is taken before the recipe runs — what its upstream's task reported, the driver's digest of that very file (`RunContext.hashed`), or its own hash — and the input has to hold its content (`content.require_fetched`) and be the same file when the recipe ends (`content.stamp`); a result left alone whose bytes the run fetched is hashed before anything reads it, since a stand-in that gives no SHA-256 vouched for nothing (`materialize._not_as_recorded`); a result that reads as a stand-in is not recorded (`content.standin`); the commit is the one the run started from, and holds every analysis read from the working tree (`worker.require_in_commit`, given `Graph.specs`); the environment is checked either side of the recipe (`_gate`). The rerun entry point refuses a tree changed by more than the result's own files. |
| `UNCOMMITTED_CHANGES` | `materialize` refuses a tree that holds work no commit does, then runs every recipe in a checkout of the commit the project is at (`checkout.take`), which every record names and which holds the analysis, the environment and the inputs as ASTRA read them. Under a sandbox the checkout is read-only apart from where results go; a run ends by asking git what its recipes changed there beyond its own results and records, and says so. |
| `WRONG_WORKING_DIRECTORY` | `worker.execute` runs the command in `Task.workdir`, its output's analysis's folder, even when the project drives it; a container is told so (`OCIBackend.workdir`). |
| `REBUILT_FROM_COMMIT` | `plan.build`: a result from a commit is no task. What reads it reads it as a run gives it, its bytes hashed and compared with its record at that commit (`worker.from_commit`). |
| `NOT_AT_COMMIT` | Kept by refusal: `plan.build` refuses a project in which a recipe would run on a commit's files, the one result ASTRA gives no command once told where a run puts them. |
| `STALE_INPUT` | `worker.unreadable`, then `worker.from_commit`: a result from a commit that ASTRA's checker does not find unchanged there, or whose bytes are not its record's — its `ABSENT_RESULT` says so where a stand-in gives a SHA-256, and a run's hash where none does — is read by nothing; what reads it is blocked, and `--check` says what it can tell without fetching, of a task a run would hand a worker: one left alone reads nothing. |
| `UNRECREATABLE_ENVIRONMENT` | The IRI is `urn:lightcone:env:<env_version>`, a function of files in the record's commit. `worker.require_in_commit`, asked by `materialize` and by the rerun entry point, refuses a run while one of `identity.files`, or the analysis, is not in git as a file of its own (`dataset.not_in_git`): an ignored file leaves a tree clean, a symlink is committed as the path it points to, and an annexed file as a pointer. |

### The subprocess seam

Every external tool (uv, git, git-annex, container runtimes) is invoked through `engine.project._run`. Route new commands through it. `tests/conftest.py` stubs it with the autouse `tools` fixture, which emulates each tool's observable effect and records every argv. The `real_tools` fixture puts the real one back, and the `analysis` fixture builds a real project on top of it.

## Project rules

These came out of review and apply to every change.

- **No backward-compatibility code.** No migrations, version guards or aliases for older behavior or formats.
- **No foreshadowing and no dead code.** Code, comments, flags and messages describe only what exists now. `lc --help` lists only verbs that work.
- **No escape hatches around guarantees.** Enforcement ships without a flag that turns it off.
- **Nothing waits on a human.** Agents run these verbs: no interactive prompts, no interactive shells.
- **Literal behavior over invented convenience.** Erroring beats guessing; anything ambiguous is a `ProjectError`.
- **Streamline.** No small helpers or rendering layers where a few inline lines read fine.
- **Never reference design documents or section numbers in code or comments.** Comments and docstrings carry *why*, not the history of how the code came to be.
- **Attribute adapted third-party material** as "inspired from" or "adapted from", with its license. The Seatbelt profiles in `sandbox/profiles/` are kept near-verbatim from upstream so they can be diffed.
- **Leave working files alone** when a nearby change merely makes them look touchable.
- **A dependency lands with the code that needs it.**

## Conventions

- Ruff (E, F, I, N, W, UP), line length 100, target py311. mypy strict with `namespace_packages` and `explicit_package_bases`.
- Google-style docstrings on public functions. Click command callbacks are the exception: their docstring is the `--help` text and stays prose.
- `worker.py` and `_sandbox_exec.py` are on the `python -m` path of every task. Keep `worker.py` free of click and rich; keep `_sandbox_exec.py` stdlib-only with no lightcone imports.
- `image.py` is pure. Test its structure and ordering, not byte goldens; the one byte-level claim is that rendering twice gives identical output.

## Testing patterns

- Tests mirror `src/`. Pure suites (`test_identity`, `test_content`, `test_plan`, `test_image`, `test_sandbox_policy`, `test_sandbox_wrap`, `test_sandbox_denial`, `test_sandbox_oci`) spawn nothing and run on any OS.
- `test_dataset`, `test_worker`, `test_materialize` and `test_checkout` run real git, git-annex and uv on purpose. Whether bytes land in the annex, whether git-annex stays out of a checkout and whether the tree ends clean are questions a stub cannot answer.
- A graph test's scheduler runs each task where `submit` is called and hands results back from `completed`: overriding one of the two is how a test does something to the project while a run is in flight (an edit, a commit, a second run). A recipe's `pwd` is its checkout's; `conftest.ran_in` names the folder in it.
- `materialize.cluster_for_run` is the monkeypatch point for graph tests that should not launch a real cluster.
- `test_publish.py` runs real git and git-annex against a GitHub made of local bare repositories (`conftest.GitHub`, the `github` fixture): git is sent there in github.com's place by `url.<folder>.insteadOf`, and the REST API is answered from the same folder. The store is a directory, the one kind that needs no account. Nothing in the suite reaches GitHub: the autouse `no_github` fixture fails any API call, hides `gh` and drops ambient tokens. What is tested of Git LFS and of ssh is what lc tells git-annex, never what GitHub or a cluster then does.
- `test_runner_rules.py` has one test per rule of the specification's runner layer lc keeps, named after its code, on a real project; `test_false_record` asks ASTRA's own checker (`astra.api.status`) whether what lc wrote holds.
- `test_plan.py` tests what lc adds (which results are tasks, what each task looks up, edges, the refusals), not what a spec means, and drives `classify()` with the statuses ASTRA's checker returns, built by hand: what is pinned is what lc makes of them. Every fixture spec must pass `astra validate`.
- Identity tests check sensitivity both ways: what must move the hash and what must not.
- `test_sandbox_enforcement.py` runs the real `exec_policy` against the real kernel mechanism, with one suite for both Landlock and Seatbelt. **Mutation-check every new denial test**: run the same command through `Unavailable()` and confirm it succeeds, otherwise the test proves nothing.
- `test_cli.py` covers the CLI surface only. Rich wraps at terminal width, so assert on short fragments.

## Invariants and traps

Each of these was learned from a real failure or a measurement, and most are not visible from the code at the point where you would break them. Lines marked *measured* were checked empirically; do not re-derive them from defaults.

### CLI and convergence

- `cli/commands.py` imports the engine inside command callbacks and builds the rich console lazily, so `lc --help` and completion stay cheap. `astra.api` loads the whole library, so the engine imports it inside the functions that use it, `project.converge` included.
- Whatever `lc` prints in colour takes it from one palette, Lightcone Research's (`_PALETTE` in `cli/commands.py`), and the six marks every verb speaks with are constants beside it, named by what they say. A terminal never says whether its ground is dark or light, so a tone has to read on both: the darker ones are mixed toward white until they do (*measured*: Blue Ink as given is 2.5:1 on a dark ground). rich leaves a tone it does not know unstyled without a word, so a test names every tone the marks and the banner use; its highlighter is off, since its cyan, magenta and green are no tone of the palette. The banner of `lc init` is for a person: it prints only where the output is a terminal. A blank cell of its mark is U+2800, never a space.
- `converge(write=False)` is check mode: the same decision path with side effects off. Everything routes through `_Converger.item` / `.file` / `.blocked`. A *warning* never affects `converged`; a *blocked* item does.
- Convergence only appends to files the user owns. `.gitignore` and `.gitattributes` converge entry by entry, never by a marker. **A new managed `.gitattributes` line goes at the end of the template**, because the file is last-match-wins and the disorder check judges against template order.
- Only what git can carry is converged (no empty directories), so a fresh clone needs nothing but `.venv` and `git annex init`.
- `uv.lock` and `.venv` converge by correctness, using uv's own `--check` probes. Those probes are why the scaffold sets the uv floor: an older uv rejects the flag and convergence would silently re-lock forever.
- Every uv call carries an explicit `--project`. `--system-site-packages` must never be used. `project.child_env` scrubs ambient `UV_*` outside the `_UV_KEPT` allowlist, because those variables change what a lock installs without moving `env_version`.
- There is one project uv hop, `project.uv_prefix`, always `--no-sync`: the driver converges before submitting, and a per-task sync would have workers racing on `.venv`.
- Don't add a flag whose only user is a test; stub `project._run` instead.

### Storage

- `filter.annex.required=true` is set by convergence. Without it, on Linux a `git add` whose annex filter cannot start exits 0 and stages the raw bytes into git history (*measured*). lc writes no absolute paths, filter drivers or hooks into a repository.
- `* annex.largefiles=nothing` must come first in `.gitattributes`; without it `filter=annex` annexes code too. Records are exempted back into git so a clone with no content can still classify, and the `.astra/**` line comes last, so no line above it reaches a record.
- `materialize._require_storable` asks git about the very paths a run would commit, before anything runs: a clone where git-annex was never set up, a result an ignore rule covers, a result no line sends to the annex, and a record a line does send there are each refused by name — whether by `annex.largefiles` or by a `filter` other than git-annex's, such as the line `git lfs track` appends. The rules are files the researcher owns, and each of these fails silently otherwise. Both questions are asked NUL-separated, or git quotes a path holding an accent; `check-ignore` takes `-z` only with its paths on stdin (*measured*).
- An `annex.largefiles` expression can turn on the bytes (`largerthan=`), which do not exist before the run, so the preflight refuses only what the attributes settle, and `dataset.save` checks where git staged a result and its records (`git annex lookupkey` on the index) before it commits. Refused, nothing is committed and nothing is left staged.
- A `git add` through the annex filter leaves the location log in git-annex's journal; a clone made before a git-annex command commits it is told of no copy (*measured*). `dataset.save` commits it after each commit with `git annex sync --only-annex` and no remote, content or commit of its own. Never `git annex merge`: with no ref it merges a pending `synced/` branch into the branch checked out (*measured*), in the middle of a run.
- A refused save is put back (`checkout.land`): nothing committed, and the result's files as the last commit has them. A commit git itself refuses leaves nothing staged either (`dataset.save`): what stays staged goes into whoever commits the index next, a merge the researcher concludes or their own commit.
- git-annex routes dotfiles to git regardless of `annex.largefiles`, so `dataset.save` passes `annex.dotfiles=true` per add. The image archive lives under a dot path and depends on it.
- Results are committed with `annex.thin=true` per add, never in repo config. Thin's hazard is an in-place write, which rewrites the annex object under its key (*measured*: the committed version becomes unrecoverable). lc never writes in place; researchers' tools on `data/` do. In tests, unlink a result before forging it, since identical results share one object.
- An unfetched annexed file still exists: as a small pointer file (unlocked) or a dangling symlink (locked), and Git LFS leaves a pointer file of its own. `content.standin` reads a pointer file exactly as ASTRA's checker does (a whole Git LFS pointer, a one-line annex path, at most 1024 bytes): read any other way, an input ASTRA calls content is refused, or a result is recorded that ASTRA then reads as a stand-in and plans again forever. `content.require_fetched` refuses all three with `ContentNotFetchedError` before a file is hashed; hashing one would give a well-formed digest of the wrong thing. ASTRA reads each as a stand-in, which gives the content's hash without the content, so read-only verbs classify a bytes-free clone correctly; content that is stood in for remakes nothing while a remote of the clone holds it. Which file a run fetches is ASTRA's checker's answer (`Bytes`): what git-annex keeps is fetched, and content another tool keeps (Git LFS, DVC) is refused before anything runs, naming the command that fetches it.
- `dataset.save` commits with the same pathspec it stages, so work the user staged mid-run is never swept into a result's commit. Every git command waits out another's hold on `index.lock` (`dataset._run`): a plain `git add` of a large file holds the lock for as long as hashing it takes (*measured*). A lock that outlasts that wait is refused before work that ends in a commit starts, a run or `lc build` (`dataset.require_free_index`), since a killed git leaves it for good.
- `dataset.status` is scoped with `-- .` because a project may sit inside a larger repository. It counts a submodule that differs at all, whatever `.gitmodules` asks git to ignore, and untracked files whatever `status.showUntrackedFiles` says — passed as `-c`, the one form that also reaches the `git status` git runs inside a submodule. It reads git's NUL-separated form with renames off: git otherwise quotes a path holding a space or an accent, and no comparison with a real path then holds. What `git status` calls modified is then compared (`git diff`, in `dataset._filled`): git takes a file for changed on its size alone where the index entry was made from a stand-in, which is what an annexed file is from the moment git-annex gives it its bytes until that command ends (*measured*). Uncompared, a run that starts while another fetches is told to commit the inputs being fetched, and a commit's tree another run is fetching into reads as changed (`commits._intact` asks `git diff` too). Only a file of the size its key in the index names is compared: any other is a change, and git-annex's filter copies what it is given into the annex (*measured*: a changed input, or a result another run has yet to commit, written a second time). The comparison carries `diff.autoRefreshIndex=true`, without which git lists a file on its stat alone (*measured*).
- `dataset.restore` is `git reset` for what was staged, `git clean`, then `git checkout HEAD --` only for paths HEAD has. Never `git checkout HEAD -- .`. Without the reset a path staged and in no commit stays, staged: `clean` leaves a file of the index and `checkout` cannot match it (*measured*).
- `require_committer` runs before a run, not at the first commit, so a missing git identity cannot waste a computed result.
- `pyproject.toml` re-declares the git-annex wheel's entry points so `uv tool install` puts `git-annex` on PATH. A test pins them against the wheel. Under `uvx` the researcher's own `git add` cannot find git-annex; that is why `required` is set.
- lc never imports datalad and never parses `.datalad/`. It writes there (dataset id, image archives, container config) and reads back only through `git config -f`. datalad is a dev dependency because the run record's format is datalad's: the suite parses it with datalad and runs a real `datalad rerun`, since a malformed record makes `rerun` skip and exit 0.

### Identity and classification

- `env_version` is length-framed (`_frame`). It hashes raw lock bytes rather than a parse, and a closed settings list (`_INSTALL_SETTINGS`) with every key hashed whether set or not. `uv.toml` replaces `[tool.uv]` rather than merging (*measured*), and settings are read the way uv reads them.
- Machine-level uv config (`~/.config/uv/uv.toml`, `/etc/uv/uv.toml`) is never hashed, only reported as an advisory: hashing it would make one commit classify differently on two hosts. No uv flag closes the gap without also dropping the project's own config (*measured*).
- The git commit is recorded and never hashed. **Editing analysis code remakes nothing unless the file is declared as an ASTRA input.** That is a decision; do not add a heuristic that scans recipes for paths.
- The engine version is attestation (the record's `runner`), never identity: an lc upgrade moves no result.
- The lock scan refuses path, directory and editable dependencies, because they record where code was, not what it was. Names compare in PEP 503 form.
- `stale` and `missing` mean the result contradicts the project; `behind` means only circumstances moved. `stale` wins when both apply. `behind` does not propagate downstream.
- `Verdict.calls_for_a_remake(refresh=)` is the only place a state becomes an action. Do not re-spell it at a call site.
- The driver and a task differ by one input value to `classify()`, never by logic: `read`, the bytes of each result this one reads, which only a task knows once its upstreams are made or kept. Without it the checker's `stale_inputs` are taken as they are.
- ASTRA's checker says what a result breaks in itself (`Status.why`) and, separately, which entries read a result that is not unchanged or was made again with other bytes (`Status.stale_inputs`). A result stale only through those is ok again once they are made with the bytes its record gives: a task compares the bytes its upstreams came out with against those its record says were read, which is what lets a byte-identical rebuild stop a cascade. Only an error in `why` stales. `ABSENT_RESULT`, a warning, is bytes at the result's place that are neither the record's nor a stand-in for them: lc calls the result `stale`, since what is there is not what its recipe made, and a run makes it again, since no clone can fetch what the record names. What reads it read the recorded bytes, so it stays ok until a rebuild gives others. Unfetched content stood in for is no diagnostic at all.
- A skip returns the recorded digest, never a recomputed one, so bytes-free clones classify correctly.
- `--refresh` widens a run by exactly one state. There is no flag that suppresses remaking a stale result.
- `lc status` always exits 0 and tolerates a dirty tree; `materialize --check` is the gate. `up_to_date` ignores `behind` and is false for a failed run.

### Execution

- ASTRA's checker and the container runtime are read once per run by the driver and handed down. HEAD moves as the driver commits, so a per-task read would be nondeterministic. A record's `commit` is the one the run's checkout is of: the commit the project is at when the checkout is taken, which holds the analysis as ASTRA read it (`Graph.checked.head`) and may follow that commit.
- A task asks ASTRA nothing. It applies `classify()` to the findings it was handed and never calls `astra.api.status` or git: compute nodes need neither, and a check per task would cost a full pass over the analysis each time. The one astra call in a task is `write_records`.
- A result's digest (`sha256:` hash and size) is computed in the worker before anything is staged, by hashing the file the recipe wrote. It must not come from the annex, where nothing is recorded yet. What a task read of another task is the digest that task reported, for the very file it was taken of (`TaskOutcome.stamp`, as `RunContext.hashed` does for inputs); any other file in its place is hashed as the recipe reads it, so a record never names bytes its recipe did not read.
- A declared input more than one task of a run reads is hashed once, by the driver: each task would otherwise read all of it to name it in its record, and a multiverse reads one catalog in every universe. The digest travels with the stamp of the file it was computed from (`content.stamp`: inode, size, time), and a task takes it only for that very file; for any other it hashes what it reads.
- A dependent can start before its upstream is committed. That is safe: the worker has moved the file to its place before it reports, and committing it there gives it one more name, in the annex, without moving, replacing or writing it. Do not move the commit into the task.
- A result with two names is one file: the recipe writes its first place, the worker copies the bytes to the others, and `write_records` writes a record at each; a run stores and commits every place.
- The worker resets only what the result owns (`Task.owns`: its file and its records), never the directory, since results share it and run concurrently. A file a recipe writes beside its result is no output's: it stays in the run's checkout and goes with it, and the run warns that it was not kept. A result declared again in another format is a new artifact at a new place; the earlier file is only no longer declared, and stays committed. A payload that is not a regular file — a symlink, a folder, nothing — fails the task.
- `materialize` converges the environment once something is to run, before any recipe starts, in the run's checkout: from the lock its commit holds, never the project's own `.venv`, which is the researcher's. `uv run --locked --no-sync` does not notice a `.venv` that drifted from the lock (*measured*). A fresh environment per run is what that costs (*measured*: 0.3 s to install 12,000 files from a warm cache on the same local disk, 3 s with its bytecode compiled).
- The run fetches what its recipes read itself with `git annex get`, where ASTRA's checker finds the bytes absent and kept by git-annex: every file a task that may run reads, bar a result certain to be remade — a result that may run only because something it reads may is left alone when that comes out as recorded, and its readers then read its bytes. A run that makes nothing fetches nothing, and connects to no cluster. `lc fetch` brings the bytes of current results, and nothing else: a stale or missing one is made again, never fetched. Read-only verbs never transfer anything. Nobody is ever told to run an annex command by hand. A fetched result is hashed before anything reads it; one whose bytes are not its record's is reported failed and its readers blocked, and with its bytes in the clone, the next check plans it.
- A file git checks out is a stand-in until git-annex fills it in from its annex. Its hooks do after a checkout or a merge, but `git reset --hard` and `git stash` leave a stand-in even then, and nothing does where `core.hooksPath` sends git's hooks elsewhere (*measured*). ASTRA's checker reads such a file as bytes the clone lacks, so every verb that reads the analysis first runs what those hooks run, `git annex smudge --update` (`dataset.populate`), where git-annex is set up: no transfer, and nothing git compares changes. A copy in the clone's own annex is therefore never a place to fetch from.
- Which remote holds a result's bytes is git-annex's log, read offline by one `git annex whereis --json --batch` for every result whose bytes the clone lacks (`dataset.holders`). `whereis` first merges what each remote's `git-annex` branch brought, a commit on that branch alone, HEAD and the tree untouched (*measured*); with `annex.merge-annex-branches=false` it misses the copies a `git pull` told of, and a result a remote holds would be made again. Only a repository the clone has as a remote counts (`remote.<name>.annex-uuid`): the log also names repositories it cannot reach — a colleague's, once they push the log but not the bytes — and `get` fails on those (*measured*). Read-only verbs refuse a clone git-annex was never set up in rather than ask it: asking sets it up (*measured*), without the rest of what `lc init` converges.
- The log says what was last heard of a remote. `git annex get` reports a remote that lost a copy exactly as one it cannot reach (`Unable to access these remotes`) and leaves the log as it was (*measured*), so every later fetch would try it again and nothing would remake the result. After a failed fetch `dataset.get` asks each remote the log names (`fsck --from --fast`), which drops a copy the remote lost from the log and leaves an unreachable remote alone (*measured*): a lost result is `missing` from then on, an unreachable one stays where it was.
- A file at another commit is given in that commit's tree, never fetched into the project's (`commits.give`). A tree kept from an earlier run is reused only while it is still that commit's — checked out at it, no tracked file changed; one git cannot read is not — and made again otherwise: what a recipe reads at a commit is hashed as found. A tree that cannot be given blocks every task of the run that reads a file of it, and what depends on those; the rest still runs. A result from a commit that ASTRA's checker already says nothing is built from is not fetched: its readers are blocked for that reason. A commit astra-tools names no repository for, which the project's does not hold, is a submodule's, which only its checkout holds: it is refused, and what reads it is blocked. For the project's own commit the content is fetched into the project first, from wherever the project fetches its own, and the commit's clone takes it with `get --from origin`: the clone's git-annex branch was copied before the project held it, so a plain `get` finds no copy (*measured*). git-annex initializes itself in that clone at its first fetch, which commits, so the clone carries the project's committer identity (*measured*). The run record lists only the files of the dataset, which datalad can fetch; the worker gives the rest.
- An analysis in a folder of the project keeps its results in its own `results/`, which the project's anchored `results/**` line does not reach: the storage check refuses such a result and names the line that does, `<folder>/results/** annex.largefiles=anything`, for the end of the project's `.gitattributes`. Nothing annexes a folder merely named `results`.
- What holds for the project's own folders holds for each analysis read from the working tree. lc alone writes the `results/` and `.astra/` of an analysis in a folder of the project, as it does the project's (`materialize._written`): a change there is no work of the researcher's, so the dirty-tree refusal leaves those folders out, and comes after the graph is read. A probe is granted that analysis's inputs, as its recipes are (`run.input_paths`); an input declared at another commit is no file of the working tree. A root-anchored `results/` or a lone `analyses[0]` misses all of it, and no test of a single analysis notices.
- The project's tree receives only whole results: a worker moves a file there once its recipe has ended and its record is written, and what a task that failed, was blocked or never ended left is in the run's checkout. A change where results go therefore refuses no run. It is a result a run made and has not committed yet, or never did, and a run settles each before it plans (`materialize._adopt`): one whose record is a true one of its bytes is committed, since ASTRA's checker would find it unchanged for ever and no checkout would hold it; any other the checker already reads as stale or missing, and the run makes it again.
- The run record pins the engine with `uv run --no-project --with <requirement>`: a release by version, a dev build by source commit (`materialize._engine_requirement`). The worker entry point syncs the project environment itself. Recorded paths are declared, never resolved, or they would name annex objects.
- Concurrency is the allocation's. There is no `--jobs`.
- Recipes run through `bash -c`.

### Checkout

- **git-annex never runs in a checkout, nor does Git LFS.** Run in a linked worktree, by a hook or by the filter a bare `git status` starts, git-annex fills every annexed file it holds the bytes of, by copy, and replaces the worktree's `.git` file with a symlink (*measured*; `git worktree remove` then refuses the worktree). Git LFS, checking a commit out, downloads every file it keeps, or fails the checkout where one cannot be had (*measured*: `smudge filter lfs failed`). Every git command lc runs there carries `dataset.PLAIN` (no hooks, neither tool's filter), and whatever lc starts there, `uv sync`, the `uv run` around a recipe and the recipe, runs in `Runtime.env`, which carries the same as environment (`dataset.plain_env`, numbered after whatever the ambient environment already tells git that way): a build backend that asks git for a version starts git-annex as surely as a recipe's own `git status`. A new command in a checkout takes one or the other. `test_checkout` pins both measurements, each both ways.
- git takes bytes at an annexed path for the commit's only where its index entry was made from bytes: an entry made from a stand-in records the stand-in's size, and git reports the file modified without asking any filter, which no `git update-index --refresh` changes (*measured*). So in a checkout, where annexed files are checked out as stand-ins, `checkout.fill` marks every one `--assume-unchanged`; and in the project's tree a result is added in place, as content, never checked out and filled.
- That is why a run does not commit in its checkout and merge: the project's tree would receive each result as a stand-in, which only git-annex's own populate turns into bytes git accepts, and that populate copies (*measured*).
- **A result is written once.** git-annex stores a file that has two names by copy, whatever `annex.thin` says (*measured*: a second write of every result, and two copies until the checkout is gone). So a result never has two: the worker gives it its name in the project's tree and takes away the one it had (`checkout.hand_over`), which is a rename's cost whatever its size, and `checkout.land` commits it there as `dataset.save` commits one made in place (*measured*: one inode for the project's file and the annex's object, no byte copied). What the checkout keeps is a link to the project's file, for the tasks that read it; `content.stamp` follows it, so the stamp a worker took before the move is the file's after it.
- A task goes on after the driver that submitted it is gone, and would end by putting its file over what a later run has committed. Its scheduler knows: Dask tells a worker that nothing holds a task's result any more while the recipe runs on. The worker asks before it moves anything (`worker._abandoned`), and a task whose run is gone leaves its result in that run's checkout.
- The worker moves the file, not the driver, and before it reports: what reads a result starts once its task has reported, so it never finds the place empty, and the policy it runs under, built then, grants the file the link leads to (`test_sandbox_enforcement`: denied to a recipe that does not declare it). The record comes with the task's report (`TaskOutcome.records`), and `land` gives it its place with the commit: once a task has reported, its run reads nothing in the checkout, which another run removes once the allocation has ended, whether or not this one is still committing.
- **The plan is of the checkout's commit, or the run does not start.** ASTRA is asked about the project's tree, which keeps its checker's cache and lets a run with nothing to make take no checkout; the checkout is of the commit the project is at when it is taken, which every record names. That is a later commit than the plan was read at wherever the image converge committed an archive, which the record's commit has to hold, or another run a result. So three things are checked. `plan.build` refuses only an analysis that changed between ASTRA's two answers (`dataset.same` on the spec files), never a commit that left it alone. The run refuses a commit that holds another analysis, environment or input than the plan was read at. And before anything is submitted, each result the run may leave alone has to be, by its record in the checkout, the one the plan read (`materialize._recorded`). Without the last a reader takes the plan's digest for the checkout's file.
- **What is where results go is settled before a run plans** (`materialize._adopt`). A result is in the project's tree before it is committed, so a driver that died in between leaves bytes there, with their record where it died after placing it, and so does the rerun entry point run by hand. A record that is a true one of its bytes is committed as its run would have, unless the history no longer holds the commit it names, where it is put back as a landing refuses it; nothing else there is trusted, and ASTRA's checker already reads it as stale or missing. Two runs may commit one such result, the one landing it and one that found it: whichever commits second finds nothing left to commit, which `dataset.save` reads as committed, where git tracks the files and they are as the last commit has them: a path someone's `git reset` or `git stash` unstaged in that instant differs from no commit either, and is not committed (*measured*): the run ends there, in git's words, with the place put back. Adopted are the bytes that are the record's when they are staged, hashed again and compared with what git-annex staged them under: ASTRA's checker read them a moment before, and another run may have moved a result of its own there since, which is that run's to commit. Planning from a tree that holds a true record no commit does was the alternative, and it commits records that name bytes no recipe read: the tree's record, the checkout's file.
- `checkout.fill` gives bytes to what a task that may run reads, and removes every other file a tool keeps, git-annex or Git LFS, from the checkout. Left as the stand-in git stores, a file no output declares would be read all the same, a line of text for data, by a recipe that then exits 0 (*measured*); removed, the read fails by name. A file a task does read whose bytes this clone lacks stays a stand-in, which the worker refuses by name (`content.require_fetched`). Which object an annexed file is a name of is asked of the checkout's commit (`dataset.annexed`), never of the project's tree, which may have moved.
- A file a task reads is given as the run's commit means it, never as the project's tree holds it by then: an annexed file from the annex, by its key at that commit, and what Git LFS keeps, which is its pointer in a checkout, from Git LFS's own store in the repository (`dataset.lfs_objects`), by the object the pointer names. What DVC keeps beside a `.dvc` file is a file git ignores, so that no commit holds a file of it: it alone is given from the project's tree. ASTRA refuses any other input git does not track.
- A name is a hard link, made beside its target and renamed over it. Where the filesystem makes none (two filesystems, or a file someone else owns), it is a copy, as git-annex falls back to one.
- The bytes that are committed are the ones the worker hashed. Before a landing, the file's stamp says so at no cost, and where it does not, the bytes are hashed again: a stamp taken on one node need not compare with one taken on another, since GPFS documents that a file's times may lag across nodes. And the file waits where other runs write, for as long as a landing waits for the index: so what git-annex staged it under is compared with the worker's digest before the commit (`dataset.save`, `named`), where that key names a SHA-256.
- Between `git add` and the commit a result is staged in the index the researcher commits from, for the instant git-annex takes to say where it went (*measured*: 55 ms). Two things can happen in it, and neither is closed, by decision: git gives no way to stage and commit under the one lock it holds for its own commits, and a commit made from an index of lc's own would leave the researcher's index saying the result is deleted. A commit of the whole index made in that instant takes the result and its record, a true pair, which the run reads as committed and says has no run record of its own. And a file another run replaces in that instant is committed under this run's record, until that run commits its own.
- git commits nothing else in a tree while a merge or a cherry-pick is under way there (*measured*: `cannot do a partial commit during a merge`), and a commit made during a rebase goes with it when the rebase is abandoned (*measured*). So a run does not start in such a tree, and a landing waits for one the researcher began since (`dataset.under_way`), for as long as it waits for the index.
- A result lands only while the project's history holds the run's commit (`dataset.is_ancestor`): commits the researcher adds during a run are fine, and a branch switched or rewritten away from the run's commit ends the run, loudly, with that result put back as the last commit has it.
- A result is committed after each result of the run it read, whatever order the reports come in, so the history is in the order of the graph and `datalad rerun` over a range makes a result before what reads it. Dask hands a report over once it has fetched it (`as_completed`, one fetch per task), which need not be the order the tasks ended in: a report that came before one it depends on waits (`materialize`, `early`). Results that read nothing of each other are committed as they are reported, in any order: each commit is of one result's own files, and every record names the run's commit, not the one before it.
- A result that read one the run did not commit is not committed either (`_consume`, `unlanded`).
- Two runs that make the same result at once each move theirs into place, whole, and each commits only the bytes its own worker hashed: the later move is what the branch ends with, and the other run says its file is no longer its record's. Where the other was already committing its own, putting its place back takes the later file with it, and both say so: the next run makes the result.
- `git add` hashes under the project's index lock: a landing holds it for as long as git-annex takes to hash the result (*measured*: 7 s per GiB on local disk), and another run's landing waits that long for it (`checkout.LANDING`), where every other git command gives up after `dataset._PATIENCE`. A lock a killed git left is found before a run starts.
- Several runs fetch into one annex, and git-annex refuses a transfer another of its processes holds (*measured*: `transfer already in progress, or unable to take transfer lock`, and the content is there once the first is over). Every fetch a run makes goes through `dataset.transfer`, which asks again.
- A checkout is locked as it is made (`git worktree add --lock --reason <allocation>`), so no run ever finds another's unheld; `checkout.require_git` refuses a git older than 2.33 before anything is prepared. The run that took it removes it once every task it submitted has reported, however the run went; left any other way (an interrupt, a killed driver, a dropped ssh session), it stays until `compute.phase` says its allocation has ended, since a recipe may still be writing there. Unknown is never ended: a checkout held by a local allocation of another host or boot stays, and every run names it, with the command that removes it.
- `git worktree remove`, forced twice, removes a locked worktree with its ignored files. It refuses a folder whose `.git` is not the file git wrote, and forgets one whose folder is gone (*measured*): `checkout._remove` removes what is left of such a folder, then asks again.
- The world a run enters is resolved, and its image built, from the project's tree, after the run has read its commit. `Runtime.at` refuses a checkout that declares another: the gate either side of a recipe reads the checkout, which never changes.
- uv reads the settings of the first project above one that has no `[tool.uv]` of its own, and from a checkout that is the researcher's `pyproject.toml`, mid-edit or not (*measured*). An empty `.lightcone/runs/uv.toml` stands between the two.
- The trees of other commits (`.lightcone/commits/`) are given in the project, once for every run, and a checkout holds a link to them: ASTRA's commands name them from the project root. Two runs may give one commit's tree at once, so a clone is made under a name of its own and removed where it does not become the tree, and one a killed run left is removed once it is a day old; a tree that is no longer its commit's is made again, unless a run holds a checkout: its recipes may be reading the tree, with the files that run fetched there, so it is refused until none does (which is why a run reaps before it gives).
- A checkout's submodules are not checked out, and a run names each: ASTRA refuses an input in one, so what a recipe reads there is undeclared, and it finds an empty folder.
- A container sees what is mounted, and a checkout's `.git` only names the repository: `container.policy_for` and `container.sync` mount the repository where it is, read-only, and give git the plain options, so git in the image answers for the run's commit as it did when the project's own tree was mounted. A host mechanism grants no git to run, so nothing of the repository is granted there.
- The run record's paths are measured from the project root, and the commit it is in is in the project: `datalad rerun` runs in the project's tree, with no checkout.
- Unmeasured, by decision: a shared filesystem. What NERSC documents (2026-11): `$HOME` and CFS are GPFS, reached natively from login nodes and through DVS from compute nodes, where file locking is not supported; scratch is Lustre. GPFS makes no hard link across filesets, and a checkout is in the project's own folder. So the driver, the one process that runs git, git-annex and `uv sync`, belongs on a login node or on scratch, which was so before checkouts; workers only read, write, rename and link files. A checkout's environment is tens of thousands of files for the length of a run, against an inode quota (1 M in `$HOME`). When a real project shows one of these behaving otherwise, what was seen becomes a line here.

### Publication

- **No lc message prints a git-annex command, and no agent runs one.** An agent keeps plain git for its own work (`git add`, `git commit`, `git pull`) and uses lc for everything that touches data: `lc fetch` to read bytes, `lc publish` to share, never `git annex get`, `push`, `sync` or `verifyremote`. Who may read a project, where its data lives, and confirming a store are the user's: an agent asks, lays out the options and recommends none.
- A plain `git push` sends commits only: every clone then sees those results as `missing` (*measured*). Nothing breaks: the next `lc publish` from a clone that holds the bytes sends them. `git annex push` and `git annex sync` are not used: they push `synced/` branches, sync merges, and push may drop by preferred content (*measured*). lc copies exactly the keys it means to (`dataset.send`) and pushes two refs, the branch and `git-annex`.
- Bytes go first so that no commit reaches a clone before the bytes it names: where a send fails, neither the log nor the commits go, and `lc publish` exits 1. Only a key git-annex answers for as sent was sent: for one its log places in the clone and its annex does not hold, `copy --batch-keys --json` answers with an empty line and exits 0 (*measured*). Whatever lc can tell beforehand is refused before anything is created or sent: a file above 5 GB bound for Git LFS, and a directory that cannot hold a store, which is why the store is made before the repository is.
- A store is what git-annex's branch declares, not what it is called: a special remote git-annex enables by itself (`autoenable=true` in `remote.log`). lc declares one as `origin-storage` (`dataset.STORE`), in Git LFS or in a directory, and one declared by hand or by another tool, under another name, is the project's store all the same: read from, confirmed and published to (`dataset.stores`). One of another kind, a bucket say, is the project's store too: read from, and `lc publish` refuses rather than declare a second beside it (`Store.kind` is None for it; git-annex's own type for a special remote in a folder is `directory`, which is not lc's store in a directory, a `type=git` repository). A second address of a store is a line of its own in `remote.log`, which names the store by `sameas-uuid` and itself by `sameas-name` (*measured*). A project that declares several stores is published to none: which one would be a guess, and a clone sends nothing while one of them is unconfirmed. A special remote that is no git remote has no `url` in a clone's configuration, only git-annex's id for it (*measured*): where it is comes from its declaration.
- A clone learns which repository its store is from the store's declaration in git-annex's branch (`Store.uuid`, its line of `remote.log`), not from its own configuration: for a store in a directory, git-annex writes `remote.<name>.annex-uuid` only once it has looked there (*measured*), in the declaring clone too. Read from the configuration alone, everything in a store not yet reached, or unmounted, would be `missing`, and made again.
- A store has to be one git-annex enables by itself in a clone, since nothing else tells a clone where it is. `type=git-lfs` and `type=git` are; a `directory` special remote is not, its path being no part of what is stored (*measured*). So a store in a directory is a bare git-annex repository lc makes there (`git init --bare --shared=group`), declared as `type=git`.
- git-annex 10.20261026 sends nothing, to any remote, from a clone that has an unconfirmed special remote, a plain `git push` included, through its pre-push hook (*measured*; CVE-2026-112818). It records where a store stands in `remote.<name>.annex-verified`: `verified` in the clone that declared it or confirmed it, `automatic` where git-annex enabled it by itself, `manual` where it was enabled by name (*measured*). Reading from an `automatic` store is free; a `manual` one cannot even be read until confirmed, so lc never enables a store with `git annex enableremote` (*measured*). The floor in `pyproject.toml` is that version, and `publish.require_annex` refuses an older one on `PATH`: it would send to a store nobody confirmed.
- lc never confirms a store by itself. `dataset.confirm` takes the code `git annex verifyremote <name>` shows with the declaration and gives it back (`--safe <code>`), so what is confirmed is what was shown; and it confirms only a declaration that is, setting for setting, what lc declares for the place the user repeated (`publish._settings`). A declaration that carries anything else is not lc's to vouch for. The clone's own configuration says what is in effect, never what is being confirmed: a change a pull brings to a store's declaration takes effect only once confirmed.
- git-annex enables a declared store when it is first set up in a clone. In a clone already set up, `git annex init --autoenable` refuses unless forced, since it cannot tell whether another of its processes is running (*measured*). `dataset.enable_store` forces it, before anything reads git-annex's log, wherever a declaration has no remote in the clone: the store comes up `automatic`, as in a fresh clone, a store the clone already has keeps its standing (*measured*), and the one thing that sends to a store, `lc publish`, checks that it is confirmed first. What a `git pull` brought of git-annex's branch is merged only when one of its commands runs (*measured*), so declarations are read from the clone's `git-annex` branch and from each one a remote brought, the newer line of two holding, as git-annex merges them. A store marked dead stays declared and is enabled by nothing (*measured*): it is not waited for.
- Set up beside an `origin` over https, git-annex asks that URL for a `config` file, twice, and marks the remote `annex-ignore` when it gets none (*measured*). `lc init` has to work offline, so convergence writes `remote.origin.annex-ignore` itself for an `origin` on GitHub, before `git annex init`. DataLad marks a sibling on GitHub the same way. Declaring a Git LFS store asks the same question of its URL and goes on without an answer (*measured*).
- What a clone keeps of where the project is published is two settings no clone gets from another: `annex-ignore` on `origin`, and `remote.origin.datalad-publish-depends`, which has `datalad push --to origin` send bytes to the store first (*measured* with DataLad 1.6: it copies, then pushes; to a store in a directory it pushes the branches as well, which changes nothing). `dataset.unsettled` names them, convergence and `lc publish` write them.
- `git annex find --branch=<commit> --anything` lists what a commit names, from the top of the repository, whatever the working tree holds; `lookupkey --ref --batch` answers one line per file, empty for one git keeps itself; `whereis --json --batch-keys` and `copy --batch-keys --json` take keys, and `copy`'s answers then carry no file (*measured*). `copy --fast` takes the log's word that the store lacks a key, where git-annex otherwise asks the store about each before sending.
- git-annex keeps what a copy told it in its journal, and merges what a remote's `git-annex` branch brought only when one of its commands runs: `dataset.record_copies`, the sync of that branch alone that `dataset.save` uses, does both (*measured*), and runs before every push. A push GitHub refuses means someone published in between: their log is fetched and merged the same way, and the push tried once more, unless the branch itself moved, which is a `git pull`.
- Nothing lc runs waits on anyone. `project.child_env` turns git's prompts off for every tool, and `dataset.reaching` puts ssh in batch mode for each command that reaches a remote: every fetch, of a result, an input, a commit's tree or the image, and everything `lc publish` sends. A new command that reaches a remote takes those options too. git takes its ssh command from `core.sshCommand` and git-annex its options from `annex.ssh-options`, each ignoring the other's (*measured*: given `core.sshCommand`, git-annex runs its own ssh without it), so both are passed, each on top of what the repository already sets; a `GIT_SSH_COMMAND` in the environment is taken as it is. The one ssh lc runs itself, to make a store on another host, is the same command (`dataset.ssh`).
- Many paths go to git and git-annex on standard input (`--batch`, `--batch-keys`, `--stdin`), never as arguments: a multiverse has more results than a command line holds. `git annex fsck` takes files as arguments only, so it gets them a bounded number at a time. A GitHub token in the environment is offered to git through a credential helper scoped to `https://github.com`, which names the variable and never holds the token: no command line and no file carries one, and no other host is offered it.
- A project is online when its `origin` is a repository on GitHub (`dataset.target`): the one definition `lc init`, `lc status` and `lc publish` share. An address may carry a user or a token, which lc never shows (`github.without_credentials`) and never writes into a store's declaration.
- The repository a URL names is created only with a token, found in `GH_TOKEN`, `GITHUB_TOKEN`, then `gh auth token` where `gh` is installed. Whether it exists is git's answer (`ls-remote`), with git's own credentials; the API says who can read it, and a repository git reaches that GitHub shows to nobody is private.
- Publishing does not depend on the analysis being valid: one that cannot be read is a warning, and what it reads at other commits is then left out. A commit with stale or missing results is published as it is, and said.
- Unmeasured, by decision: Git LFS on GitHub (credentials, quotas, refusals) and ssh to a cluster. lc quotes whatever either says and parses none of it. When a real project shows one of them behaving otherwise than the documentation says, what was seen becomes a line here.

### Sandbox

- **Never grant EXECUTE on a directory that could be a system prefix.** Landlock unions rights over ancestors, so one grant on `/usr` silently defeats the per-file allowlist while every test passes. The interpreter's file is always executable; its install root only when it is the interpreter's own tree.
- Three non-obvious grants, each found by a failure: the realpath'd ELF loader in the exec set, read on the interpreter's install root (the stdlib), and read on `/dev/urandom`.
- A derived read root may never be `$HOME` or above (`_stdlib_root`).
- Tool paths resolve through `policy.utility()` only. A hardcoded `/usr/bin/env` is a denial on the first exec of every run on hosts that keep it elsewhere.
- The env overlay is applied inside the wrap by the seam (`boundary.env_argv`), never merged into the subprocess environment: the `uv run` hop outside the boundary must keep the real `XDG_*`, or uv loses its cache.
- The overlay sets `PYTHONDONTWRITEBYTECODE`, never `PYTHONPYCACHEPREFIX`: with a cache prefix Python reads bytecode only from there, so the environment's own, compiled when it was synced, is ignored and every run compiles everything it imports (*measured*: three times the import time of a scientific stack).
- `Unavailable` is a real backend that attests `fs: open`. There are no sandbox flags.
- `denial.trailer()` fires on every nonzero sandboxed exit, because `denial.explain()` may find nothing. Remedies must be things that work today.
- The shim exits 97 on any setup failure and never runs the command unsandboxed. Its policy arrives as JSON on argv, which keeps `wrap` pure.
- SBPL is last-match-wins while Landlock unions. `generate_profile` restates the write tier after the read-only guard; in the wrong order, recipes work on Linux and fail on macOS.
- The mechanisms disagree about removing the write root itself: Landlock denies it, Seatbelt allows it. A test asserting either answer fails on the other OS.
- A recipe's write scope is the directory its result lands in, not the file: a path that does not exist yet is dropped from the policy, and a file grant cannot create the file. A probe gets `results/` whole.
- The policy is built from the tree a recipe runs in. In a run that is the checkout, so the project's own working tree is out of a recipe's reach (`UNDECLARED_READ`), and so is the repository: `git` is not in the exec set, and a checkout's `.git` only names it.
- The write scope is a directory nested in a read-only tree because that is the only shape Landlock, SBPL and bind mounts all express. A writable tree with a read-only hole needs subtraction, which Landlock lacks.
- `/dev`, `/proc`, `/sys` and `/run` are granted generously on purpose. The test for any grant is whether undeclared *inputs* could arrive through it; a grant whose absence produces an unattributable error should be made freely.
- On macOS, not controlling the network needs the mach services in `network.sbpl`, not only the socket families. The vendored profiles carry one marked local delta (no blanket `process-exec`), pinned by a test.
- Enforcement fixtures must not live under `/tmp`, which is in the write baseline. A write-denial test must target a path the OS itself would allow, such as a declared input.

### Containers

- The engine never enters the image. Only the environment converge (`container.sync`, into `.lightcone/venv`) and each recipe or probe exec run in it; the driver, git, annex and Dask stay on the host. The host `.venv` is unused in containerized mode.
- The image is the system layer only: base, apt packages, a pinned uv and interpreter. No project file enters the build context, so a code edit can never trigger a build.
- An image's identity is its id, the sha256 of the archive's config blob. Execution pins the id the runtime's own store gives it, never a tag: the image id under podman and Docker's classic store, a manifest's digest under Docker's containerd store, a fresh Docker 29's default (*measured*). That digest is the one the archive's OCI index names when `docker save` wrote it; podman saves no index, and Docker then makes the manifest as it loads, so its digest is read right after the load off the tag the archive carries — podman's spelling, `localhost/<tag>:latest`, which the bare tag does not reach (*measured*) — and such an archive is loaded again by every run. A dropped archive is never substituted; a rebuild is a new archive under a new id.
- `runtime_for_run(root, *, build)` has two strictnesses. `lc build` and the materialize preflight may build, save and commit. The probe and the worker only find, fetch and load.
- `lc build` refuses a tree in which a file the image is derived from is uncommitted (`identity.files`, and `.datalad/config`, which its commit carries), and a run one that holds work of the researcher's. Nothing else is `lc build`'s concern: a run in flight keeps results it has not committed yet where results go. A run's build happens after the graph resolves, so a spec typo never costs one, and the archive's commit is scoped to its own paths: the archive and `.datalad/config`, never the archive's folder, where another build's partial archive may be, which no line sends to the annex.
- The OCI wrap uses `--read-only` (otherwise a stray write succeeds into the ephemeral layer and vanishes), `--security-opt label=disable` (SELinux), and mounts with a resolved source and the declared destination. The container environment is an allowlist.
- `contains_prefix`: a host mechanism keeps the `uv run` hop outside the wrap, while the container backend takes it inside and applies env with `--env`.
- podman-hpc, podman and docker are spellings inside one `OCIBackend`, detected in that order. `_PODMAN_FAMILY` is asked positively so a new runtime does not inherit podman behavior. `podman-hpc migrate` runs outside the load branch.
- `_require_arch` refuses a wrong-architecture archive before loading: the load would succeed and fail later as `exec format error`.
- The archive format is docker-archive because every runtime consumes it, including a future apptainer backend.
- The image identity document feeds `env_version`; the tag also hashes the rendered Containerfile. A generator change therefore rebuilds the image without putting results behind.

### Compute

- `run` and `materialize` never create compute. `materialize --check` and `status` never connect to any.
- Workers run the driver's own interpreter (`sys.executable`), so client, scheduler and workers are one installation on a shared filesystem. Workers need neither git nor git-annex.
- Cluster names are native labels found by fresh discovery, not a registry. Slurm jobs are `JobName=lc-<name>` with a token in `Comment`; owner, name and token are all verified before attaching or cancelling. A user's own job named `lc-…` blocks the name loudly and is never adopted.
- Compute formats (IDs, records, catalog, JSON) are unversioned because allocations are ephemeral.
- The catalog is selected only through `LC_COMPUTE_CONFIG`, so every verb sees the same one.
- One local allocation per user per machine, enforced by scanning the process table. `flock` is not used because NERSC home filesystems do not support it. Local compute is blocked on recognized NERSC login nodes.
- Local clusters end when idle through Dask's own `idle_timeout`. `SCHEDULER_CONFIG` pins scheduler settings so ambient Dask config never applies.
- Ended local allocations are retired (`ended.json`), never deleted: a missing record cannot be told from a changed `connection_root`.
- Slurm workers are stock Dask Nannies, one per rank, with `memory_limit=0` because Dask does not account for subprocess memory. Thread-count variables default to 1.
- Recipe resources are cooperative Dask reservations, not OS limits. A recipe `time_limit` is refused. A GPU recipe takes the worker's whole GPU mask. GPU visibility comes from the allocation's `CUDA_VISIBLE_DEVICES`; nothing probes hardware.
- At NERSC, `UV_CACHE_DIR` must be off `$HOME`, since compute nodes cannot lock files there. The user exports it before `lc compute launch`.

## Decided against

Do not reintroduce these without a new reason.

- **A launcher, or the engine as a project dependency.** The `lc` that was invoked is the engine. Project locks carry only what the analysis imports.
- **`lc verify` and `lc export`.** A full rehash is O(bytes) and blind on unfetched content, while ASTRA's checker answers from records and stand-ins on a bytes-free clone.
- **Bare-recipe run records.** `datalad rerun` executes the recorded string literally, so a recipe would replay unconfined and write no record.
- **bubblewrap.** Its advantage is rights subtraction, which the policy never needs. Reconsider only if a policy shape needs subtraction or `bwrap` becomes universal.
- **Controlling the network.** Every mechanism attests `network: allowed`. `denied` stays in the type for a mechanism that really denies.
- **An exclusion-based read policy.** A missing allowlist entry fails loudly; an exclusion list fails silently.
- **Pinning the annex filter or hooks to the engine's executable.** It writes durable state pointing into a prunable `uvx` cache.
- **Asking ASTRA's checker from a task.** It needs git and the whole repository on every compute node, and pays a full check per task downstream of a rebuild. The driver asks once; a task applies lc's rule to what it was handed.
- **A second file beside the record.** The record is all lc writes beside a result. Its schema is closed, so what it cannot hold (what the sandbox enforced, the image id, the uv version) is not kept, by decision; a slot for runner attestation is a change to the specification.
- **A definition hash.** What a result is made from is the specification's to say and its checker's to compare.
- **Asking git who last wrote a result.** ASTRA's checker compares the bytes at a result's place with its record; all history added was a record forged together with its bytes, for a `git log` per result on every status.
- **Launching Slurm workers through `uv run --with`.** It re-resolves Dask away from the driver's and needs an index on compute nodes.
- **Catalog `connections`, `lc compute --config`, and a separate local settings block.** Offers name their provider, and local offers are ordinary offers.
- **Running recipes in the project's working tree.** It is where the researcher works and where another run writes: a record names a commit only a private checkout can promise.
- **Committing in the checkout and merging.** A run as a branch would leave landing to git, but git accepts a result's bytes in the project's tree only where they were added in place, and git-annex in a linked worktree copies everything it holds.
- **Recipes writing straight into the project's `results/`.** A file half made would be there, a failed task would leave one, and two runs that make the same result would write one file at once. A recipe writes in its checkout, and its worker moves the whole file.
- **Linking a result into the project and letting git-annex copy it.** The first form of landing: a second write of every result, two copies for the length of the run, and the result left read-only.
- **Kept, numbered checkouts, and lock directories between runs.** A run takes a tree nobody else has and git serializes the commits, so nothing is chosen and nothing is locked. What a kept checkout saved is the environment's sync.
- **One environment for every checkout.** A packaged project is installed into its environment by path, so a shared one would run another tree's code.
- **Migrations.** ASTRA 0.0.x specs and their `universes/*.yaml` are not read, and results from older engine layouts are invisible; the remedy is `git rm -r results/` and a re-materialize.
- **Scaffolding an `AGENTS.md` into projects.** A test pins its absence.
- **`lc init` creating a repository on GitHub**, public or private. It has to work offline, in CI, in clones and on compute nodes, and an agent would put unpublished work online. It ends with the two `lc publish` forms instead.
- **A default store.** Git LFS on GitHub has limits that are a decision (2 GB per file, 10 GiB free, nothing deletable), and many groups keep their data on their own cluster. `--data` is asked once, with no default.
- **`lc clone`, `lc pull`, `lc push`.** `git clone` then `lc init`, and `git pull`, already do the job; `lc publish` converges, so there is no second verb to learn.
- **Letting agents run git-annex.** The tool owns every data movement, as in DataLad: `git annex push` writes `synced/` branches and may drop, `git annex sync` merges, and a copy a remote lost goes unnoticed.
- **Depending on DataLad, or shipping lc as a DataLad extension.** Compatibility comes from keeping every fact where DataLad looks, not from calling it.
- **Declaring the store in `pyproject.toml`.** A second source of truth beside git-annex's branch, which is where git-annex and DataLad already look.
- **Confirming a store automatically**, even the Git LFS of the clone's own `origin`. Until a security review says otherwise, the user repeats where the data goes.
- **Making a public project private again.** Copies made while it was public remain; lc offers no way back.
